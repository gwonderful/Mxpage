# MXPAGE 稳定性、出图速度与 Token 消耗审计

日期：2026-09-14。审计对象：当前本地工作区，包括尚未提交的 Codex 账号接入及前序修复，不等同于远端主分支。

> 后续状态：本报告保留修复前证据。2026-09-14 已实施一轮稳定性修复，已修内容、测试结果及仍未实施的性能/持久队列建议见 [修复与验证记录](MXPAGE_BUG_FIX_VERIFICATION.md)。不要把下文的旧源码行号和复现输出视为修复后的行为。

## 1. 结论先看

目前最应优先处理的是任务状态、失败恢复和取消一致性，其次才是提高并发、缩短提示词。否则加速可能同时放大重复请求、重复消耗和状态错误。

- **已用隔离测试复现 3 个缺陷**：10 项中 4 项失败时父任务仍为 SUCCESS；不支持的重试先将任务改成 PENDING 再报错；心跳写入可覆盖新进度。
- **出图慢有实测依据**：当前样本成功单图平均 151.119 秒；9 张补生成串行耗时 1,353.197 秒，即 22 分 33 秒。
- **每张图生成前还会做一次带图的提示词优化**。10 张成图中，6 张保存的是备用提示词。这说明优化并非总能提供最终采用的结果，但不能据此认定 6 次都超时或推算扣除了多少额度。
- **目前无法准确统计 Codex 通道的 token 消耗**。缺少请求级 usage、推理强度、分阶段耗时和备用提示词原因。字符数、调用数只能作为替代观测指标，不能当作真实 token。
- 当前本地样本有 **4 张头图 + 6 张详情图**，10 个 PNG 文件存在，导出任务记录也是 4 + 6。这既不能证明所有批次稳定，也不能解释用户所说的“十张只有六张”。按用户要求，暂时跳过该次场景定位，不计算所谓“60% 成功率”。

本轮只调查和生成文档，没有修改业务代码、重新规划、补生成图片、改账号设置、提交或推送代码，也没有发起真实模型调用。

## 4. 稳定性与功能问题

优先级：P1 为下一轮应优先修复的正确性/数据风险；P2 为配置、性能和可观测性改进。以下均为当前发现，不是本轮已经修好。

### B01 · P1 · 部分生成失败，父任务仍标记成功【已复现】

证据：[workflow-task-service.ts](../../lib/services/workflow-task-service.ts)，`runGenerateAllSectionsTask`，433 行循环、486 行异常处理、514 行收尾；[task-service.ts](../../lib/services/task-service.ts)，111 行 `completeTask`。

逐项失败被捕获并累计 `failedItems`，循环结束仍无条件调用 `completeTask`，后者写入 SUCCESS。隔离测试让前 6 项成功、后 4 项抛出普通生成错误，得到：

```json
{"status":"SUCCESS","totalItems":10,"completedItems":6,"failedItems":4,"currentStep":"generate_all_finished"}
```

影响：只按父任务 status 判断的任务列表、自动化或下游处理会把部分失败理解成全部成功。前端规划页 503 行还检查失败和取消计数，会给出不同提示，因此不能说界面完全隐藏了失败。

建议：明确“全部成功/部分完成/全部失败/取消”合同。若暂不扩展枚举，可用 FAILED 加保留完成计数表达部分失败；若引入 PARTIAL_SUCCESS，必须同步 API、前端和数据模型。保留成功图片，仅对明确失败/缺失的模块补做。

验收：覆盖 10/10、6/10、0/10、部分取消、账号级失败提前停止；各计数与状态一致，后续补图不重做已有成功图片。

### B02 · P1 · 不支持的重试会先污染任务状态【已复现】

证据：[workflow-task-service.ts](../../lib/services/workflow-task-service.ts)，748 行 `retryWorkflowTask`，758 行先改状态，804 行最终抛错。

函数先将任务改成 PENDING、清除错误和结束时间，再判断任务类型。只处理 BATCH_CREATE、TRANSLATE_PAGE、XHS_GENERATE；GENERATE 等类型落入不支持错误。实际源码的隔离结果：

```json
{"error":"This task type does not support retry.","statusAfter":"PENDING"}
```

影响：调用通用任务重试接口后，可能出现没有执行器负责的“等待中”任务。不能假设所有界面都会展示这个重试入口，但服务接口本身存在该路径。

建议：先验证类型、输入和可重试终态，再原子认领；不支持的请求不得写数据库。不要直接把所有类型都接到整批重跑，应分别定义恢复语义和尝试记录。

验收：不支持的类型在请求前后数据完全不变；同一任务同时重试两次，只能认领一次。

### B03 · P1 · 心跳和进度的读改写竞争【已复现】

证据：[task-service.ts](../../lib/services/task-service.ts)，93 行 `updateTaskProgress`；[workflow-task-service.ts](../../lib/services/workflow-task-service.ts)，428 行每 15 秒异步心跳。

进度更新先读取整个 outputPayload，再合并 patch 全量写回。心跳与生成循环都调用此函数，没有版本约束。隔离测试让两个调用读取同一旧快照，再依次写入：

```text
初始：currentTaskId=old-child，completedItems=0
业务更新：currentTaskId=new-child，completedItems=1
并发心跳随后写回：currentTaskId=old-child，completedItems=0
```

影响不只是进度回退：取消与过期恢复依赖 `currentTaskId`，可能找到错误的子任务。已复现可发生的竞争，不代表已证明历史批次发生过。

建议：心跳使用独立字段，不重写业务 JSON；业务进度使用单写入者或带版本号的原子更新，终态也须条件更新。给定时器 Promise 增加错误处理。

验收：控制交错顺序并发写心跳、计数、当前子任务和终态，计数不回退，终态不被旧快照覆盖，取消定位正确。

### B04 · P1 · 图片编辑取消未贯穿到模型和落库【代码确认】

证据：[generation-service.ts](../../lib/services/generation-service.ts)，918 行 `editSectionImage`，1018 行提示词优化、1047 行图片编辑调用、1134 行激活新图。与普通生成在 688 行注册 AbortController、746/770 行传 signal 的实现不同。

编辑路径没有注册任务取消信号，也没有把信号传给上述两次调用；保存和激活版本前也没有对应取消断言。任务被标记取消后，模型仍可能继续执行并替换当前图片。`completeTask` 的终态保护不能回滚之前已更新的资源和模块。

建议：复用普通生成的信号生命周期，编辑请求贯穿取消；最终资源激活用任务状态与版本的原子条件保护。保留已产生但未激活的结果时，应明确其归属，不能悄悄覆盖用户当前版本。

验收：分别在预优化期间、模型执行期间、返回后持久化前取消；任务维持 CANCELED，原图与当前版本不变。停止本地进程并不等于远端已经撤销计算或不消耗额度。

### B05 · P1 · 重新规划先删旧模块，缺少事务和历史保护【代码确认】

证据：[planner-service.ts](../../lib/services/planner-service.ts)，872 行先 `deleteMany`，随后归一化并 `createMany`；937 行 fallback 路径同样先删后建；[schema.prisma](../../prisma/schema.prisma)，179 行 SectionVersion 随模块级联删除。

如果删除之后计算或写入失败，旧模块已不存在。即使重新规划成功，也会删除旧版本记录；生成资源的 section 关联被置空，而非自动安全迁移到新模块。不能把“文件还在”当作“编辑历史仍可恢复”。

建议：先计算并校验新方案，再事务提交；用户已有图片时明确提示重规划影响。优先保留版本化规划，或在明确映射与保留规则后更新模块，不应靠按标题猜测图片归属。

验收：模拟创建失败，原模块/版本/当前图片全部保留；重规划成功也满足用户确认的历史保留规则。不要拿现有成图项目做破坏性试验。

### B06 · P2 · 是否同步补充要求，用关键词猜测【代码确认】

证据：[planner-workspace.tsx](../../components/planner/planner-workspace.tsx)，213 行 `hasSectionsSyncedGenerationRequirements`。

当前判断是：任一模块提示词包含“生图补充要求”，或包含补充要求按空白切分出的任一长片段，即认为已同步。中文长句可能没有空格；模型改写后会被误判未同步。反过来，只要有固定短语就可能把旧方案误判成已同步。

影响：提示不可信，可能诱导重复规划和额外消耗；与 B05 相结合会增加已有图片历史受损风险。

建议：记录规范化要求的版本/hash，并记录该规划实际采用的版本；不做语义关键词猜测。验收包括中文无空格、同义改写、要求更新、旧提示词含固定标签等情况。

### B07 · P1 · 进程内后台任务不能保证跨重启完成【代码确认】

证据：[task-service.ts](../../lib/services/task-service.ts)，293 行 `runTaskInBackground`；220 行 `recoverStaleBulkGenerationTask`。

后台执行由当前进程中的 Promise 持有，没有持久化执行队列。进程退出或重启后不能从数据库自动续跑；过期恢复只是标记失败，不是恢复工作。已有心跳能帮助识别遗留任务，但不能提供持久执行。

注意：不能把“单图超过 90 秒”直接认定为 stale 原因，因为心跳每 15 秒独立更新；真正风险是心跳丢失、进程退出或竞争。

建议：生产运行先避免在生成过程中切换/重启开发服务；长期按任务租约、子项状态和幂等键恢复。引入持久执行器属于后续架构变更，需单独实施和验收，不在本轮偷偷替换。

### B08 · P1 · 去重不是原子操作；账号级失败停止条件不足【代码确认】

证据：[generation-service.ts](../../lib/services/generation-service.ts)，669 行查询运行任务后另行创建，且按 GENERATE/REGENERATE 分开；[workflow-task-service.ts](../../lib/services/workflow-task-service.ts)，393 行 `isProviderWideImageFailure`。

并发请求可能同时通过“没有运行任务”的检查；生成与重绘还可能分别通过各自类型的检查。批任务账号级停止只匹配两个中文“无端点/无模型”提示，不覆盖所有配额、认证、限流错误。部分错误会被下层包装后触发停止，不能说所有账号错误都一定被忽略；但从预优化等路径抛出的配额错误可能让后续模块继续重复尝试。

建议：按模块与输入版本原子认领，建立账号级并发预算和结构化错误分类。配额/认证失败暂停整批并保留未开始项；明确瞬态错误才做有上限的退避重试。结果不明的图片超时先核对结果，避免盲目重试造成重复图片和额度消耗。

### B09 · P2 · 导出允许缺图，且两目录内文件名可能重复【代码确认】

证据：[export-service.ts](../../lib/services/export-service.ts)，26 行头图选择、59 行详情图筛选、83 行文件名、164/171 行两组索引。

- 详情模块缺少当前图片时直接被过滤。头图不足时可以混入上传的 MAIN/ANGLE 原始素材；“导出了若干图片”不等于“全部规划模块生成完成”。现有导出清单列出实际导出内容，但缺少明确的计划数量/缺失模块对账。
- 头图和详情图分别从 `01` 编号，同一时间戳下存在同名文件。ZIP 保留目录时没有冲突；若人为合并到同一目录并覆盖，4+6 张可能只剩 6 个不同文件名。这只是可解释的风险条件，**不是用户那次事件的已确认原因**。

建议：导出前显示计划/已生成/缺失数量，默认要求完整或让用户明确选择部分导出；清单加入缺失模块和素材来源。文件名带 hero/detail 或 sectionKey，跨目录也唯一。

## 5. 出图慢与 Token 优化机会

### 当前关键路径

```text
项目分析 → 页面规划
             ↓
每个模块：素材读取/编码 → 带图 Prompt Agent（预算 90s）
                              ├─ 成功：优化提示词
                              └─ 可降级错误：备用提示词
                         → 原生生图 → 保存资源/版本
             ↓
完成当前模块后，才开始下一个模块
```

“慢”不能全部归到图像模型：实测单图任务耗时覆盖以上整段路径。也不能把账号代理模型的名字当成底层图像模型的精确型号；资源 metadata 中 `usedModel` 记录的是所选代理模型。

| 编号 | 代码事实与定位 | 优化方向 | 代价/边界 |
| --- | --- | --- | --- |
| O01 | [visual-prompt-agent.ts](../../lib/services/visual-prompt-agent.ts) 19、183–205 行，每图先发一次结构化多模态请求，超时可继续用 fallback | 对 Codex 通道做“保留预优化 / 直接使用已有基础提示词”的对照；可加入同批优化超时熔断及按输入版本缓存 | 可能降低复杂构图质量，不能未经盲评直接删掉；6/10 fallback 不证明 6 次都消耗满 90 秒 |
| O02 | [generation-service.ts](../../lib/services/generation-service.ts) 711、729、760 行，参考图片在预优化和最终生成重复附加；预优化最多 3 张 | 预优化先尝试只用既有商品分析与素材元数据；必要时只看主图；最终生成保留必要原图 | 图片 token/额度影响未测；不能为了省量移除产品身份的唯一可靠参考 |
| O03 | [provider-service.ts](../../lib/services/provider-service.ts) 498–518 行，一个默认模型绑定所有角色；[codex-app-server.ts](../../lib/ai/codex-app-server.ts) 162–174 行未明确设置推理强度 | 支持按任务配置模型/推理强度，轻量辅助任务使用运行时支持的较低档位，重要规划保留质量预算 | 实际继承档位未记录；不能假设当前就是最高档。参数名和可选值实施前须对照本机协议/模型能力验证 |

## 6. 参数配置核查

以下“建议”是后续实验方案，**尚未修改任何参数**。随部署/账号变化的预算应走现有配置机制，不能把新的固定常量散落在代码里。

| 参数/合同 | 当前实现 | 建议 |
| --- | --- | --- |
| Prompt Agent 超时 | 固定 90 秒 | 配置化并记录原因；A/B 比较跳过、较短预算与现状，选择质量合格的最低延迟方案，不凭空指定最优秒数 |
| 文本请求预算 | Codex 默认 180 秒；具体调用可覆盖，例如数量决策 90 秒 | 按 operation 统计分位耗时，再分配预算；单个 174.940 秒样本只能说明余量较小，不能直接推出应延长到某个值 |
| 图片请求预算 | Codex 默认 600 秒 | 保留长任务与取消支持；按数据调整，不能用一刀切短超时伪装加速 |
| 心跳/遗留判断 | 15 秒心跳；有心跳时 90 秒无更新判 stale，无心跳时 5 分钟 | 先修复进度竞争，再按运行环境配置；租约判断与单图超时分离 |
| 并发 | 同批 1 张；不同请求缺少完整原子去重 | 先建立账号与模块约束；然后小规模测 1→2，不直接放大到 10 |
| 模型/推理 | 默认单模型覆盖全部角色；推理强度未显式指定 | 显式、可追溯、能力校验后分层，不通过更改用户全局 Codex 配置来调项目 |
| 比例/像素 | `getOutputSize` 给出 1024×1024 或 1024×1536；CodexAdapter 以自然语言发送 size 和 aspectRatio | 两者在竖图上不是同一比例合同；明确“构图比例”与“交付像素”。账号通道没有强制像素验证，需按能力校验返回尺寸并声明差异 |
| SVG 兜底 | 由项目配置允许；与备用提示词是不同概念 | 商业真图验收不能把 SVG 算真实出图成功；保留明显标识，不用开启兜底掩盖模型失败 |

本样本 941×1672 接近 9:16，而不是传入 size 的 1024×1536。若需要精确像素，必须另设明确的交付策略；不能无提示裁切导致商品或文案丢失。

## 7. 可观测性：先知道额度消耗在哪里

证据：[codex-app-server.ts](../../lib/ai/codex-app-server.ts) 的 `turn`/`runCodex` 目前只收集结果；[codex.ts](../../lib/ai/adapters/codex.ts) 不返回 usage；Prompt Agent 还设置 `suppressUsageLog: true`。现有总任务耗时无法拆出优化等待、模型执行和传输耗时。

建议每次调用记录以下最小集合，成功、失败、超时和取消都要有记录：

- taskId / parentTaskId / sectionId / attemptId / operation / providerKind；不要只记录通用 `image_api`，账号模式与 API 模式需能区分。
- model、实际生效 effort（若可获取）、文本字符数、参考图数量/字节数，以及输入版本 hash。
- 排队、启动/握手、Prompt Agent、生图、保存各阶段耗时；响应状态、结构化错误类别、promptFallback 原因。
- 如果当前 App Server 协议提供请求级 usage，读取其真实字段并保存口径；拿不到就显示“未知”。不把账号整体额度变化当作本项目精确消费，也不把字符数直接换算为实际 token。
- 原生图片工具用量与代理文本 token 分开；若仅能得到代理模型名，不冒充已识别底层生图模型。

不要记录凭据、完整 base64 图片、账号敏感信息或整段私密商品资料。记录内容长度与不可逆标识即可支撑多数性能排查。

## 9. 建议实施顺序与验收

1. **先修正确性**：B01–B05、B08；新增可控并发、部分失败、重试、取消与事务失败的回归测试。成功图片和用户编辑不能被补图流程覆盖。
2. **再补观测**：按第 7 节记录请求/阶段/原因，校正任务状态与图片清单，补充导出对账。未能采集的 token 明确显示未知。
3. **做低风险省量实验**：首先验证 Prompt Agent 按需启用/同批熔断、去掉辅助阶段重复附图、去掉重复 JSON 样例、缓存输入不变的编译提示词。每项独立对照，避免无法归因。
4. **最后提速与持久执行**：在账号限流和模块幂等保护下试验受限并发；按部署需求实施任务租约与恢复。运行环境从开发模式迁移到稳定进程属于单独变更。

建议下一轮验证矩阵：

| 场景 | 必须满足的结果 |
| --- | --- |
| 10 张全部成功 | 10 个模块、10 个有效输出文件、父任务成功、导出清单一致 |
| 人为注入 4 张失败 | 明确显示 6 成功/4 失败；父任务不冒充全部成功；只补 4 张 |
| 超时/额度不足/网络故障 | 错误类别区分；账号级故障暂停；未知结果不盲目重试；不以 SVG 伪装真图 |
| 同时点击生成/重试/重绘 | 同一模块相同输入版本最多一个有效执行；每次调用可追踪 |
| 任意阶段取消 | 不激活取消后才返回的图片；不破坏原图；明确远端取消的不确定边界 |
| 重新规划写入失败 | 原方案、历史版本和当前图片完整保留 |
| 进程重启 | 能识别遗留任务并准确说明恢复方式；未实现自动续跑前不得声称支持 |
| 提示词/并发 A/B | 相同商品、参考图、页面数、输出要求和可用模型下，记录样本量、失败数、总耗时/单图分布、真实 usage 或明确标注的代理指标 |

质量比较至少检查产品身份、中文可读性、卖点准确性、构图、页面间风格一致性；多商品、重复批次验证后再设最终性能与成功率目标。**不承诺未经测量的“提速 50%”“节省 80% token”或“零失败”。**
